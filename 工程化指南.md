# 工程化指南

> 包管理、Monorepo 与版本发布的选型与落地
> 更新：2026-11-27　·　配套文档：[项目初始化指南](项目初始化指南.md)　·　[AI 初始化指南](AI初始化指南.md)

**本文内容**

- npm / pnpm / Yarn / Bun 的差异与版本锁定
- pnpm workspace、Turborepo、Nx 的任务编排
- Changesets / semantic-release / release-please 的发布模型
- 从零搭建 pnpm + Turborepo + Changesets 的完整配方

## 1. 选型概览


| 目标              | 推荐路径                              |
| --------------- | --------------------------------- |
| 新建 Monorepo     | **pnpm + Turborepo + Changesets** |
| 单包小项目           | npm（零额外依赖）或 pnpm                  |
| 追求严格依赖 / PnP    | Yarn Berry                        |
| 安装 / 运行 / 测试一体化 | Bun                               |
| 大型多团队仓库         | Nx（依赖仍可由 pnpm 管理）                 |
| 微软系 / 强治理       | Rush                              |


> **核心判断**：包管理器决定依赖如何解析，Monorepo 工具决定任务如何编排，发布工具决定版本如何产生。三者解耦，可以自由组合。

## 2. 包管理器

### 2.1 对比


| 工具         | 初始化                               | 锁文件                 | 关键能力                                  | 官网                                 |
| ---------- | --------------------------------- | ------------------- | ------------------------------------- | ---------------------------------- |
| npm        | 随 Node 安装，`npm init -y`           | `package-lock.json` | workspaces、`npm ci`                   | [npmjs.com](https://www.npmjs.com) |
| **pnpm**   | `corepack enable && pnpm init`    | `pnpm-lock.yaml`    | 内容寻址 store、严格依赖、`--filter`、`catalog:` | [pnpm.io](https://pnpm.io)         |
| Yarn Berry | `corepack enable && yarn init -2` | `yarn.lock`         | PnP、zero-install、`workspaces foreach` | [yarnpkg.com](https://yarnpkg.com) |
| Bun        | `bun init`                        | `bun.lock`          | 安装 + 运行时 + 测试 + 打包                    | [bun.sh](https://bun.sh)           |


**选型建议**


| 场景          | 选择              | 理由                                   |
| ----------- | --------------- | ------------------------------------ |
| 新建 Monorepo | **pnpm**        | workspace、catalog、filter 能力最完整，磁盘占用低 |
| 单包 / 兼容优先   | npm             | 无需额外安装，CI 镜像默认自带                     |
| 禁止幽灵依赖      | Yarn Berry（PnP） | 依赖必须显式声明；代价是生态兼容与调试成本                |
| 工具链一体化      | Bun             | 一个二进制覆盖安装、运行、测试、打包                   |


> ⚠️ Yarn 的 PnP 模式会让未声明的依赖直接报错，迁移前先确认 IDE、构建、测试工具链是否兼容；保守做法是在 `.yarnrc.yml` 设 `nodeLinker: node-modules`。

### 2.2 版本锁定

包管理器版本要和 Node 版本一起锁定，否则会出现「本地能装、CI 装出另一棵树」：

```bash
# 推荐：用 Corepack 锁定（会写入 package.json 的 packageManager 字段）
corepack enable
corepack use pnpm@latest

# 不使用 Corepack 时
npm install -g pnpm@latest
```

> ⚠️ Node.js 25 起不再随附 Corepack，需要先 `npm install -g corepack`；Node 22 / 24 LTS 仍自带。

根 `package.json` 中应保留锁定信息：

```json
{
  "packageManager": "pnpm@11.7.0",
  "engines": { "node": ">=22" }
}
```

CI 一律用 frozen 安装，禁止在流水线里改动 lockfile：

```bash
pnpm install --frozen-lockfile
npm ci
yarn install --immutable
bun install --frozen-lockfile
```

### 2.3 pnpm 11 要点

pnpm 11（2026-04）是一次大版本升级，从 pnpm 10 及更早版本迁移时注意：


| 变化                       | 说明                                                                                    |
| ------------------------ | ------------------------------------------------------------------------------------- |
| Node.js 22+              | CLI 改为纯 ESM，旧版本 Node 无法运行                                                             |
| 配置集中                     | pnpm 设置移入 `pnpm-workspace.yaml`；`.npmrc` 只保留 registry / 认证                            |
| 不再读取 `package.json#pnpm` | 原 `pnpm.overrides` 等字段需迁移到 workspace 配置                                               |
| `allowBuilds`            | 取代 `onlyBuiltDependencies` / `neverBuiltDependencies` 等旧字段                            |
| 安全默认值                    | `minimumReleaseAge: 1440`（分钟，即 24 小时内发布的版本不解析）、`blockExoticSubdeps`、`strictDepBuilds` |


一个完整的工作区配置：

```yaml
# pnpm-workspace.yaml
packages:
  - "apps/*"
  - "packages/*"

# 工作区统一依赖版本
catalog:
  react: ^19.0.0
  typescript: ^5.9.0

# pnpm 11 默认阻止依赖执行安装脚本，按需放行
allowBuilds:
  esbuild: true
  sharp: true
```

```json
// packages/web/package.json
{
  "dependencies": {
    "react": "catalog:"
  }
}
```

常用命令：

```bash
pnpm add -Dw turbo           # -D 开发依赖，-w 装到工作区根
pnpm add react --filter web  # 只给 web 加依赖
pnpm -r run build            # 所有包按依赖顺序执行
pnpm --filter web... run build  # web 及其依赖
pnpm dlx create-vite my-app  # 一次性执行，不写入依赖
```

## 3. Monorepo

### 3.1 工具对比


| 工具              | 定位                   | 初始化                                     | 任务缓存  | 官网                                     |
| --------------- | -------------------- | --------------------------------------- | ----- | -------------------------------------- |
| pnpm workspaces | 包链接与依赖管理             | 手写 `pnpm-workspace.yaml`                | 无     | [pnpm.io](https://pnpm.io)             |
| **Turborepo**   | 任务管道 + 本地/远程缓存       | `pnpm dlx create-turbo@latest`          | 内置    | [turborepo.com](https://turborepo.com) |
| Nx              | 插件、生成器、项目图           | `npx create-nx-workspace@latest`        | 内置    | [nx.dev](https://nx.dev)               |
| Lerna           | 多包版本与发布（v8 起由 Nx 驱动） | `npx lerna@latest init`                 | 继承 Nx | [lerna.js.org](https://lerna.js.org)   |
| Rush            | 微软系、强治理              | `npm i -g @microsoft/rush && rush init` | 增量构建  | [rushjs.io](https://rushjs.io)         |
| Moon            | 任务运行 + 工具链管理         | `npm i -g @moonrepo/cli && moon init`   | 内置    | [moonrepo.dev](https://moonrepo.dev)   |


**选型建议**


| 场景             | 选择                   | 理由                              |
| -------------- | -------------------- | ------------------------------- |
| 中小型 TS / 前端仓库  | **pnpm + Turborepo** | 一个 `turbo.json` 起步，增量构建与缓存收益直接  |
| 大型 / 多团队 / 多框架 | **Nx**               | 生成器统一架构，项目图与 `affected` 适合大规模协作 |
| 已有 Lerna       | Lerna v8 或迁移         | v8 已由 Nx 驱动；新项目不建议从 Lerna 起步    |
| 强合规 / 超大仓库     | Rush                 | 版本策略、审批与发布流程严格                  |


### 3.2 Turborepo

`turbo` 装在仓库根，`turbo.json` 描述任务之间的依赖与缓存产物：

```json
{
  "$schema": "https://turborepo.com/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**", ".next/**", "!.next/cache/**"]
    },
    "lint": {},
    "test": { "dependsOn": ["build"] },
    "dev": { "cache": false, "persistent": true }
  }
}
```


| 字段                  | 作用                                  |
| ------------------- | ----------------------------------- |
| `dependsOn`         | `"^build"` 先构建依赖包；`"build"` 表示同包内顺序 |
| `outputs`           | 需要缓存的产物；不写则只缓存日志、不缓存文件              |
| `inputs`            | 参与哈希的文件；默认是 Git 跟踪的文件               |
| `env` / `globalEnv` | 参与哈希的环境变量，漏写会出现「缓存命中但产物是旧的」         |
| `cache: false`      | 部署等副作用任务不走缓存                        |
| `persistent: true`  | `dev` 这类常驻任务，配合 `cache: false`      |


常用命令：

```bash
pnpm dlx create-turbo@latest my-monorepo --package-manager pnpm

# 已有 pnpm workspace
pnpm add -Dw turbo

pnpm turbo run build lint test
pnpm turbo run build --filter=web...   # web 及其依赖
pnpm turbo run test --affected         # 只跑受影响的包
pnpm turbo run build --dry=json        # 查看任务图与哈希输入
pnpm turbo prune web --docker          # 生成裁剪后的部署目录
```

> ⚠️ Turborepo 2 起任务配置键从 `pipeline` 改为 `tasks`，旧配置不会生效。
> 💡 远程缓存：`turbo login && turbo link`，CI 中通过 `TURBO_TOKEN` / `TURBO_TEAM` 复用同一份缓存。

### 3.3 只用 pnpm workspace

不引入任务编排工具时，pnpm 本身就能管理多包：

```yaml
# pnpm-workspace.yaml
packages:
  - "apps/*"
  - "packages/*"
```

```json
// package.json（仓库根）
{
  "private": true,
  "scripts": {
    "build": "pnpm -r run build",
    "test": "pnpm -r run test"
  }
}
```

`pnpm -r` 会按包之间的依赖顺序执行，但没有缓存与任务图。包少、构建快时够用；包一多就应换 Turborepo 或 Nx。

## 4. 版本与发布

### 4.1 四种模型


| 工具               | 版本来源                            | 适合                         | 自动化程度                   |
| ---------------- | ------------------------------- | -------------------------- | ----------------------- |
| **Changesets**   | 人工提交的 changeset 文件              | 需要精确控制 semver 的库与 monorepo | 中：版本 PR 可评审，发布可手动或交给 CI |
| semantic-release | conventional commits            | 单包、发布频繁、规则稳定               | 高：合并即发布                 |
| release-please   | conventional commits + manifest | GitHub 项目、多包               | 中高：自动开 release PR       |
| Lerna version    | 手动或 conventional commits        | 存量 Lerna 仓库                | 中                       |


**选型建议**


| 需求                        | 选择               |
| ------------------------- | ---------------- |
| 多包独立版本，且要人工确认每个包的 bump 级别 | **Changesets**   |
| 单包应用 / 库，提交即发布            | semantic-release |
| 希望发布前有可评审的 release PR     | release-please   |


### 4.2 Changesets

Changesets 的核心是「变更集」文件：开发者在 PR 里声明改了哪个包、是 patch / minor / major，合并后由版本命令统一升版本、写 CHANGELOG。

```bash
pnpm add -Dw @changesets/cli
pnpm changeset init
```

```json
// .changeset/config.json
{
  "$schema": "https://unpkg.com/@changesets/config@3/schema.json",
  "changelog": "@changesets/cli/changelog",
  "commit": false,
  "fixed": [],
  "linked": [],
  "access": "public",
  "baseBranch": "main",
  "updateInternalDependencies": "patch",
  "ignore": []
}
```


| 配置                           | 说明                                                                  |
| ---------------------------- | ------------------------------------------------------------------- |
| `access`                     | scoped 包公开发布必须为 `"public"`，否则发布报 403                                |
| `fixed`                      | 组内包版本始终一致（如 React 全家桶）                                              |
| `linked`                     | 组内包只在必要时一起升，不强制同版本                                                  |
| `updateInternalDependencies` | 内部依赖的最低升级级别                                                         |
| `privatePackages`            | 需要给应用（private 包）也升版本 / 打 tag 时开启 `{ "version": true, "tag": true }` |


日常流程：

```bash
pnpm changeset                 # 选择包与 bump 级别，生成 .changeset/*.md
pnpm changeset version         # 升版本、写 CHANGELOG
pnpm install --no-frozen-lockfile
pnpm publish -r                # 发布所有未发布的版本
```

> 💡 内部依赖统一用 `workspace:*` / `workspace:^`，`pnpm publish` 时会改写为真实版本号，不要手写死版本。
> 💡 预发布：`pnpm changeset pre enter beta` 进入，`pnpm changeset pre exit` 退出；快照版本用 `pnpm changeset version --snapshot canary`。

CI 中用 `changesets/action` 维护版本 PR，合并后发布：

```yaml
- uses: changesets/action@v1
  with:
    version: pnpm changeset version
    publish: pnpm publish -r
  env:
    GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
    NPM_TOKEN: ${{ secrets.NPM_TOKEN }}
```

> ⚠️ 工作流需要 `permissions: contents: write` 与 `pull-requests: write`，并在仓库 secrets 中配置 `NPM_TOKEN`。

### 4.3 semantic-release 与 release-please


| 工具               | 工作方式                                               | 注意                                         |
| ---------------- | -------------------------------------------------- | ------------------------------------------ |
| semantic-release | 分析 commit message 自动决定版本并发布                        | 必须严格遵守 conventional commits；monorepo 需额外插件 |
| release-please   | 根据 commit 生成 release PR，合并后打 tag、创建 GitHub Release | 用 manifest 管理多包；发布 npm 包需另配 publish 步骤     |
| Lerna            | `lerna version` + `lerna publish`                  | v8 内核是 Nx；新项目优先考虑 Changesets               |


semantic-release 的版本规则：


| commit 前缀                     | 版本变化  |
| ----------------------------- | ----- |
| `fix:`                        | patch |
| `feat:`                       | minor |
| `BREAKING CHANGE:` / `feat!:` | major |


> 💡 不论选哪种工具，commit message 规范都是自动化的前提。Changesets 不强制，但统一格式能让 CHANGELOG 更可读。

## 5. 组合配方：pnpm + Turborepo + Changesets

### 5.1 初始化

```bash
mkdir my-monorepo && cd my-monorepo
npm init -y
corepack use pnpm@latest        # 写入 packageManager，锁定 pnpm 版本
```

`pnpm-workspace.yaml`：

```yaml
packages:
  - "apps/*"
  - "packages/*"

catalog:
  react: ^19.0.0
  typescript: ^5.9.0

allowBuilds:
  esbuild: true
```

根 `package.json`：

```json
{
  "name": "my-monorepo",
  "private": true,
  "packageManager": "pnpm@11.7.0",
  "engines": { "node": ">=22" },
  "scripts": {
    "build": "turbo run build",
    "dev": "turbo run dev",
    "lint": "turbo run lint",
    "test": "turbo run test",
    "changeset": "changeset",
    "version-packages": "changeset version && pnpm install --no-frozen-lockfile",
    "release": "pnpm publish -r"
  }
}
```

安装工具并初始化 Changesets：

```bash
pnpm add -Dw turbo @changesets/cli
pnpm changeset init
```

### 5.2 目录与任务

```text
my-monorepo/
├── apps/
│   └── web/                 # private: true，不发布
├── packages/
│   └── ui/                  # 需要发布的库
├── .changeset/
├── pnpm-workspace.yaml
├── turbo.json
└── package.json
```

`turbo.json`：

```json
{
  "$schema": "https://turborepo.com/schema.json",
  "tasks": {
    "build": { "dependsOn": ["^build"], "outputs": ["dist/**"] },
    "lint": {},
    "test": { "dependsOn": ["build"] },
    "dev": { "cache": false, "persistent": true }
  }
}
```

每个包的 `package.json` 只需提供同名脚本（`build` / `lint` / `test`），Turborepo 会自动按依赖图执行。

### 5.3 验收

```bash
pnpm install
pnpm turbo run build --dry=json   # 确认任务图与哈希输入
pnpm turbo run build              # 首次构建，写入缓存
pnpm turbo run build              # 再跑一次，应命中缓存
pnpm changeset                    # 记一条变更
pnpm changeset version            # 确认版本与 CHANGELOG
pnpm publish -r --dry-run         # 检查将发布的包与内容
```

> ⚠️ 只有去掉 `private: true` 的包会被发布；app 类包保持 private，避免误发。

## 6. 验收清单

- [ ] 根 `package.json` 有 `packageManager` 字段，本地与 CI 版本一致
- [ ] 仓库只有一个 lockfile，且已提交
- [ ] CI 使用 frozen 安装（`pnpm install --frozen-lockfile`）
- [ ] 任一包可单独运行：`pnpm --filter <pkg> <script>`
- [ ] `turbo run build` 第二次运行命中缓存
- [ ] 改动单个包时，`--affected` 只跑相关任务
- [ ] `pnpm changeset version` 能正确升版本并生成 CHANGELOG
- [ ] `pnpm publish -r --dry-run` 的包列表、版本与内容符合预期
- [ ] 发布工作流具备 `contents: write`、`pull-requests: write` 与 `NPM_TOKEN`

## 7. 常见坑


| 坑                                    | 现象                                | 处理                                                      |
| ------------------------------------ | --------------------------------- | ------------------------------------------------------- |
| pnpm 11 默认拦截依赖构建脚本                   | electron / esbuild / sharp 安装后不可用 | 在 `pnpm-workspace.yaml` 的 `allowBuilds` 中显式放行           |
| pnpm 11 默认 `minimumReleaseAge: 1440` | 刚发布的版本（包括刚发到 registry 的内部包）装不上    | 等待 24 小时，或临时调低该值                                        |
| 配置仍写在 `.npmrc` / `package.json#pnpm` | 升级 pnpm 11 后配置不生效                 | 迁移到 `pnpm-workspace.yaml`，v11 不再读取这两处                   |
| Node 25 没有 Corepack                  | `corepack: command not found`     | `npm i -g corepack`，或直接 `npm i -g pnpm`                 |
| `turbo.json` 仍写 `pipeline`           | 任务不执行或报 schema 错误                 | Turborepo 2 起改为 `tasks`                                 |
| 缓存命中但产物是旧的                           | 环境变量变化未触发重建                       | 在任务中声明 `env` / `globalEnv`，用 `--dry=json` 核对哈希          |
| 发布 scoped 包报 403                     | 默认按私有包发布                          | Changesets 配 `access: "public"`，或加 `--access public`    |
| 内部依赖发布后指向旧版本                         | `package.json` 里写死了版本             | 统一用 `workspace:*` / `workspace:^`，发布时由 pnpm 改写          |
| Changesets 不处理 app 版本                | private 包被跳过                      | 在 `.changeset/config.json` 开启 `privatePackages.version` |
| 多包仓库混用包管理器                           | lockfile 冲突、幽灵依赖                  | 根目录固定 `packageManager`，CI 只认一个 lockfile                 |
